# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a Requester-facing IT ticketing MVP that allows a Development Requester (selected from a seeded list as a temporary testing identity) to create IT support tickets, view and search their own tickets, open a Ticket Detail screen, and manage permitted attachments — all presented within a consistent Zen Green UI that can be reused in later labs.

---

## 2. Stakeholder Request Interpretation

The IT department needs a professional, responsive ticketing interface for end users. A Requester must be able to describe a problem, classify it by category and related system, set a priority, attach supporting files, and submit the ticket. After submission, the Requester must be able to find their ticket in a list, search and filter it, open the detail view, and add or remove attachments.

Because real authentication is deferred to Lab 3, a Development Requester Selection screen acts as a temporary "login" mechanism. The selected Requester identity controls which tickets and attachments are visible and writable. The system must enforce ownership so one Requester cannot access another's data. A consistent Zen Green visual theme must be established for reuse in future sprints.

---

## 3. Scope

### Included
- Development Requester Selection screen (temporary testing identity, not real auth)
- Create Ticket screen with validation and file attachment
- My Tickets screen with search, filter, sort, and pagination
- Requester Ticket Detail screen (read-only ticket fields)
- Attachment lifecycle: upload, download, soft removal with reason
- Ownership enforcement on all ticket and attachment endpoints
- Zen Green UI theme and reusable component conventions
- Responsive layout: desktop ≥ 992 px, tablet 768–991 px, mobile < 768 px

### Excluded
- Authentication: login, logout, passwords, sessions, tokens, role-based access
- IT Staff workflow: dashboard, queue, claiming, reassigning, changing IT Priority
- Ticket collaboration: Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle changes beyond initial New status (resolving, closing, reopening)
- Administration: user/role/reference-data management

---

## 4. Functional Requirements

- **FR-01** The system provides a Development Requester Selection screen where the user picks one active Requester before accessing any ticket screen.
- **FR-02** Only active Requesters appear in the selector dropdown; inactive Requesters are excluded.
- **FR-03** The selected Requester identity is stored in application state and displayed in the app shell for the duration of the session.
- **FR-04** A Change Requester action is available from the app shell at all times; switching reloads all Requester-scoped data.
- **FR-05** The Create Ticket screen captures: Category, Related System, Ticket Summary, Requested Priority, Description, and optional Attachments.
- **FR-06** On successful submission the backend generates a unique Ticket Number, sets status to New, and returns the Ticket Number to the frontend for display.
- **FR-07** The My Tickets screen lists only the selected Requester's tickets.
- **FR-08** My Tickets supports keyword search (Ticket Number and Summary), filtering by Category and Requested Priority and Current Status, sorting by Created Date and Last Updated, and pagination.
- **FR-09** Opening a ticket from My Tickets navigates to the Requester Ticket Detail screen showing all ticket fields as read-only.
- **FR-10** The Requester Ticket Detail screen shows the list of active attachments with download actions.
- **FR-11** A Requester can upload a permitted attachment to an existing ticket from the Ticket Detail screen.
- **FR-12** A Requester can soft-remove one of their own attachments; removal requires a reason and is irreversible.
- **FR-13** A soft-removed attachment remains visible as metadata (filename, removal date, reason) but cannot be downloaded or previewed.
- **FR-14** All ticket and attachment API endpoints enforce ownership; a Requester cannot read or modify another Requester's data.
- **FR-15** The UI provides meaningful loading, empty, no-results, and error states on every screen.

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend and must be unique. Format: `TKT-YYYY-NNNNNN` where YYYY is the year and NNNNNN is a zero-padded sequential number (e.g., `TKT-2026-000001`).
- **BR-02** A new Ticket is created with Current Status `New`. Status cannot be changed in Lab 2.
- **BR-03** Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- **BR-04** The Ticket Date is set by the backend at creation time; the frontend must not supply it.
- **BR-05** Ticket Summary is required; minimum 5 characters, maximum 150 characters; whitespace is trimmed before validation.
- **BR-06** Description is required; minimum 10 characters, maximum 2000 characters; whitespace is trimmed before validation.
- **BR-07** Category is required; must be one of the seeded active Categories.
- **BR-08** Related System is required; must be one of the seeded active Related Systems.
- **BR-09** Requested Priority is required; allowed values: `LOW`, `MEDIUM`, `HIGH`.
- **BR-10** Duplicate submission is prevented by disabling the Submit button while a request is in flight.
- **BR-11** On backend failure the form must retain all entered values so the user does not lose work.
- **BR-12** Allowed attachment types: JPG, JPEG, PNG, WEBP, PDF.
- **BR-13** Maximum attachment size: 5 MB per file.
- **BR-14** Maximum active attachments per ticket: 5. Uploading a sixth attachment when 5 are already active must be rejected with a clear error.
- **BR-15** Attachment removal is soft: the record is retained with `removedAt` timestamp and `removalReason` text; the file is no longer served.
- **BR-16** Only the Requester who owns the ticket may remove its attachments.
- **BR-17** A removal reason is required (minimum 5 characters) before soft removal is confirmed.
- **BR-18** A removed attachment must not be downloadable or previewable; attempting to download one returns 410 Gone.
- **BR-19** Attachment filenames are sanitised and stored under a server-generated unique path; original filename is stored as metadata.
- **BR-20** If a ticket is created successfully but a subsequent attachment upload fails, the ticket is retained and the user is informed that the attachment failed; the ticket is not rolled back.
- **BR-21** A Requester may only view tickets they own. Accessing another Requester's ticket returns 403 Forbidden.
- **BR-22** Inactive Requesters must not appear in the selector and cannot be used to create or retrieve tickets.
- **BR-23** The My Tickets list defaults to sorting by Created Date descending (newest first).
- **BR-24** Pagination default page size is 10 tickets per page; allowed sizes: 10, 25, 50.
- **BR-25** Search is case-insensitive and matches substrings in Ticket Number and Summary.
- **BR-26** When no tickets match the search/filter criteria, the screen shows a "No results" state distinct from the initial empty state (no tickets created yet).
- **BR-27** The Development Requester selector must be replaced by real authentication in Lab 3; no passwords, sessions, or tokens are introduced in Lab 2.

## 6. UI Specification Summary

Full details are in `docs/lab-02/ui-spec.md`. Summary below.

### Application Shell
- Top navigation bar in Primary Green (`#006B3C`) with: TokTickIT logo/title, My Tickets link, Create Ticket link, and current Requester name with Change Requester action.
- Active page is highlighted with Secondary Green (`#0B7A46`) underline or background.
- Responsive: collapses to hamburger menu on mobile < 768 px.

### Development Requester Selection Screen
- Centered card on a Pale Green (`#EAF6EF`) background.
- TokTickIT title, explanatory text ("This is for testing only and is not a login screen."), dropdown of active Requesters, Continue button (Primary), Cancel button (Secondary).
- Loading state: spinner while fetching Requesters.
- Empty state: message if no active Requesters exist.
- Error state: safe API failure message.

### Create Ticket Screen
- System-generated fields at top (Ticket Number placeholder, Ticket Date — read-only, shown as "Will be assigned on submission").
- Classification fields: Category (dropdown), Related System (dropdown), Requested Priority (radio or dropdown).
- Requester field: read-only, pre-filled from selected Requester.
- Ticket Summary: single-line text input, required.
- Description: multiline textarea, required.
- Attachments: file upload zone below main fields; shows selected files with remove-before-submit option.
- Actions: Submit (Primary, shows busy/disabled state while submitting), Cancel/Reset (Secondary).
- Success state: green banner with generated Ticket Number and "View Ticket" link.
- Validation messages appear immediately below the relevant field.

### My Tickets Screen
- Page title "My Tickets", Create Ticket button (Primary, top right).
- Search bar (searches Ticket Number and Summary).
- Filter row: Category dropdown, Requested Priority dropdown, Current Status dropdown.
- Sort controls: Created Date, Last Updated (toggle asc/desc).
- Ticket list as table on desktop; cards on mobile.
- Columns: Ticket No., Summary, Category, Requested Priority, Current Status, Created Date, Last Updated.
- Pagination controls at bottom.
- Loading, empty (no tickets yet), no-results (filters returned nothing), and error states.

### Requester Ticket Detail Screen
- Breadcrumb: My Tickets > Ticket No.
- All ticket fields displayed as read-only using distinct read-only field styling.
- Attachments section: lists active attachments with filename, size, upload date, and Download button.
- Removed attachments shown as greyed-out metadata rows with removal reason; no Download button.
- Add Attachment button (Secondary); upload dialog with file picker.
- Remove button per active attachment (Destructive style); confirmation modal requires a reason.
- Back to My Tickets link.

### Component States
See `ui-spec.md` for full details: editable, read-only, invalid, disabled, focused, loading, empty, no-results, error, success, busy.

### Responsive Rules
- Desktop ≥ 992 px: multi-column layout, centered, max-width 1200 px.
- Tablet 768–991 px: two-column layout where practical.
- Mobile < 768 px: single column, fields stack vertically, touch-friendly buttons, no horizontal scroll.

## 7. Data Changes

### New Models

#### RequesterUser
| Field | Type | Notes |
|-------|------|-------|
| id | Int (autoincrement) | PK |
| name | String | Required |
| email | String | Unique, required |
| isActive | Boolean | Default true; inactive excluded from selector |
| createdAt | DateTime | Default now() |
| updatedAt | DateTime | Auto-updated |

#### Ticket
| Field | Type | Notes |
|-------|------|-------|
| id | Int (autoincrement) | PK |
| ticketNumber | String | Unique, backend-generated, format TKT-YYYY-NNNNNN |
| requesterId | Int | FK → RequesterUser |
| categoryId | Int | FK → Category |
| relatedSystemId | Int | FK → RelatedSystem |
| summary | String | 5–150 chars |
| description | String | 10–2000 chars |
| requestedPriority | Enum (LOW, MEDIUM, HIGH) | |
| status | Enum (NEW) | Default NEW; extensible in Lab 3 |
| ticketDate | DateTime | Set by backend at creation |
| createdAt | DateTime | Default now() |
| updatedAt | DateTime | Auto-updated |

#### RelatedSystem
| Field | Type | Notes |
|-------|------|-------|
| id | Int (autoincrement) | PK |
| name | String | Unique, required |
| isActive | Boolean | Default true |
| createdAt | DateTime | Default now() |

#### Attachment
| Field | Type | Notes |
|-------|------|-------|
| id | Int (autoincrement) | PK |
| ticketId | Int | FK → Ticket |
| originalName | String | Original filename from user |
| storedPath | String | Server-generated unique storage path |
| mimeType | String | Validated MIME type |
| sizeBytes | Int | File size in bytes |
| uploadedAt | DateTime | Default now() |
| removedAt | DateTime? | Null = active; set on soft removal |
| removalReason | String? | Required when removedAt is set |

### Relationships
- RequesterUser → Ticket: one-to-many
- Ticket → Attachment: one-to-many
- Category → Ticket: one-to-many
- RelatedSystem → Ticket: one-to-many

### Indexes
- `Ticket.ticketNumber` — unique index
- `Ticket.requesterId` — index for ownership queries
- `Ticket.createdAt` — index for default sort
- `Ticket.status`, `Ticket.categoryId`, `Ticket.requestedPriority` — indexes for filter queries
- `Attachment.ticketId` — index for attachment lookups
- `RequesterUser.email` — unique index
- `RelatedSystem.name` — unique index

### Design Decision
`removedAt` (nullable DateTime) is used for soft removal rather than a boolean `isRemoved` flag. This records the exact time of removal without requiring a separate status enum, and is straightforwardly extensible if an audit log is needed in a later lab.

### Seed Data
All seeds use upsert to be idempotent:
- **Categories (4):** Account and Access, Hardware, Software, Network
- **Related Systems (6):** Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Corporate Laptop
- **Active Requesters (4):** e.g., Jennifer Anderson, Michael Brown, Sarah Johnson, David Lee
- **Inactive Requester (1):** e.g., Alex Turner (isActive: false)

## 9. Acceptance Criteria

- **AC-01** Given valid ticket data, when the Requester submits the form, then one Ticket is saved, a unique Ticket Number in format `TKT-YYYY-NNNNNN` is returned, and the success state displays it.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My Tickets or Create Ticket, then the Requester Selection screen is shown.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is requested by ticket number, then the API returns 403 and the ticket data is not shown.
- **AC-04** Given the Create Ticket form is submitted with Summary left blank, then a validation message appears below the Summary field and the API is not called.
- **AC-05** Given the Create Ticket form is submitted with a Description shorter than 10 characters, then a validation message appears below the Description field and the API is not called.
- **AC-06** Given a file larger than 5 MB is selected for attachment, then an error message is shown and the file is not uploaded.
- **AC-07** Given an unsupported file type (e.g., `.exe`) is selected, then an error message is shown and the file is not uploaded.
- **AC-08** Given 5 active attachments already exist on a ticket, when the Requester attempts to upload a sixth, then the API returns 409 and an error is displayed.
- **AC-09** Given the Requester selects a valid attachment and submits, when the upload succeeds, then the attachment appears in the Attachment list with filename, size, and upload date.
- **AC-10** Given an active attachment exists, when the Requester clicks Remove and provides a reason of at least 5 characters and confirms, then the attachment is soft-removed: `removedAt` is set, the attachment row shows as removed metadata, and the Download button is gone.
- **AC-11** Given a soft-removed attachment, when a direct download URL is requested, then the API returns 410 Gone.
- **AC-12** Given the Requester has tickets, when they open My Tickets, then only their own tickets are listed in Created Date descending order by default.
- **AC-13** Given tickets exist, when the Requester searches by a keyword in the Summary, then only matching tickets are shown.
- **AC-14** Given tickets exist, when the Requester filters by Category, then only tickets in that Category are shown.
- **AC-15** Given more than 10 tickets exist, when the Requester views My Tickets, then pagination controls are shown and navigating to page 2 loads the next set.
- **AC-16** Given no tickets match the current search/filter, then a "No results" message is shown (distinct from the empty-list state).
- **AC-17** Given the Requester is on My Tickets, when they change the selected Requester, then the ticket list refreshes to show only the new Requester's tickets.
- **AC-18** Given the backend is unavailable, when the Create Ticket form is submitted, then a safe error message is shown and all form values are preserved.
- **AC-19** Given the Development Requester Selection screen loads, when the API call succeeds, then only active Requesters appear in the dropdown.
- **AC-20** Given a valid Ticket Number, when the Requester opens Ticket Detail, then all ticket fields are displayed as read-only.
- **AC-21** Given the Create Ticket screen is viewed on mobile (< 768 px), then all fields stack vertically, no horizontal scroll occurs, and all buttons remain touch-friendly.
- **AC-22** Given required fields show a red asterisk, when the field is in error state, then a validation message appears immediately below the field (not only at the top of the form).
- **AC-23** Given the Submit button is clicked and the request is in flight, then the button shows a busy/loading state and cannot be clicked again.

## 11. Assumptions and Decisions

- **Ticket Number format:** `TKT-YYYY-NNNNNN` using a database sequence or `MAX(id)+1` padded to 6 digits within the year. This is simple to implement without a separate counter table and produces human-readable, sortable numbers.
- **Requester context storage:** The selected Requester is stored in React context (not localStorage or a cookie) so it resets on page refresh — appropriate for a testing mechanism that is not real authentication.
- **`requesterId` passed in request body:** Since there is no auth token in Lab 2, the `requesterId` is sent in the POST /api/tickets request body. The backend validates that the `requesterId` belongs to an active Requester. This will be replaced by a JWT claim in Lab 3.
- **Attachment storage:** Files are stored on the local filesystem under `server/uploads/` in Lab 2. A cloud storage migration path is not required until a later lab.
- **`relatedSystemId` in schema:** `RelatedSystem` is modelled as a separate table (not an enum) because the list of systems is expected to grow and is seeded from the database, consistent with how `Category` was implemented in Lab 1.
- **IT Priority field:** IT Priority is assigned by IT Staff and is out of scope for Lab 2. The field is not present on the Create Ticket form and is not stored in Lab 2.
